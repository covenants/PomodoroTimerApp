FocusFlow — Android Pomodoro & Timer App: Project Specification

Version: 2026-11-09 · Project document for a coding agent

1. Overview

FocusFlow is a native Android app (Kotlin + Jetpack Compose) that combines a Pomodoro focus timer with general-purpose countdown timers and a stopwatch. It must ring on time even with the screen off, and it should look and feel premium from day one. "FocusFlow" is a working name; change it before launch after a trademark and Play Store search.

Product promise: "Start focusing in one tap, see your progress every day, and never miss a timer."

Goals for v1.0

  1. A rock-solid timer engine. Timers stay accurate to within 1 second after 60 minutes in the background, through Doze, the app being killed, and a device reboot.
  2. A Pomodoro flow that works in one tap: Focus 25 → Short break 5 → after 4 rounds, Long break 15. Every value is configurable.
  3. Light gamification and statistics (streaks, daily goal, a growing visual) that bring users back each day. This is the retention lever the top-grossing apps use.
  4. A freemium model with a one-time "Pro" unlock and an optional subscription. Free users get no intrusive ads during focus sessions.

Target users

Success metrics (first 90 days after launch)

  • Crash-free sessions ≥ 99.5% and ANR rate < 0.47% (Play Console's "bad behavior" threshold).
  • Timer accuracy: 0 user reports of late or missed alarms when permissions are granted.
  • Day-7 retention ≥ 20%. Day-30 retention ≥ 8%.
  • Free→Pro conversion ≥ 2% of monthly active users.
  • Play Store rating ≥ 4.6.

2. Market research: top-grossing focus timer apps

Forest leads the category by a wide margin on both stores. The apps that earn money all pair a timer with one of three things: a reward loop (trees, pets), task management, or phone-distraction blocking. A plain timer on its own earns very little.

Lessons for FocusFlow

  • Win on Android quality. Forest's Android rating (4.59★) trails its iOS rating (4.81★), and the best-known minimalist timers (Focus Keeper, Be Focused, Session) are Apple-first. There is room for an Android timer that is premium and reliable.
  • Gamify progress, lightly. A visual reward for each completed session (a growing plant or a filling jar) plus streaks drives the daily habit.
  • Bundle tasks. Focus To-Do proves that linking sessions to tasks keeps users.
  • Monetize with IAP first, ads carefully. On Android, ads fund free users. Never show ads during a focus session, and offer a one-time "remove ads / Pro" purchase alongside a subscription.
  • Simple timers are table stakes. General countdown timers broaden the audience but do not earn money by themselves. They feed the Pro funnel (for example, unlimited presets are Pro).

Monetization

  • Pro, one-time purchase: about $4.99. Unlocks themes, unlimited presets and tags, full stats history, sounds, and removes ads.
  • Pro subscription (optional, v1.1): about $1.99 a month or $11.99 a year, for sync and future premium content. Keep the one-time purchase as well. Android users respond well to it, and Forest's IAP-led model shows it works.
  • Ads (free tier only): a single adaptive banner on the Stats screen. Never show an interstitial during or straight after a focus session. Use Google's UMP SDK for consent in the EEA and UK.
  • Paywall: shown after the third completed session and when the user taps a Pro feature. Never at first launch.

4. UX and screens

The app opens straight to the Focus screen, so a session starts with one tap. There are four bottom-nav destinations: Focus, Timers, Stats and Garden. Settings and Pro sit behind the top-bar icons. The wireframes below are original layouts for the coding agent to follow. They are not copies of competitor apps. For visual inspiration, look at the store screenshots of Forest, Focus To-Do and Flora in Section 2.

The progress ring is the hero of the app. It must read from 2 m away, and it should drain smoothly rather than jump once a second.

Most interaction happens outside the app. The notification, widget and alarm must offer the same controls as the Focus screen.

Accessibility requirements

  • Every control has a contentDescription. The timer announces its remaining time on demand, never every second.
  • Touch targets ≥ 48 dp. Text scales to 200% without clipping. Contrast ≥ 4.5:1.
  • Phase is never shown by colour alone. Always pair colour with a label ("Focus" or "Break").

5. Technical architecture

Build a single-activity Compose app on Clean Architecture + MVVM, with one TimerEngine as the only source of truth. The engine never counts ticks. It stores when a timer ends and derives the remaining time from the monotonic clock. The OS alarm guarantees the ring, and the UI only draws.

The UI, widget and notification all observe the same engine state. AlarmManager wakes the app at endAt, even if the process was killed.

Core data model

enum class Phase { FOCUS, SHORT_BREAK, LONG_BREAK }

sealed interface TimerStatus {
    data object Idle : TimerStatus
    data class Running(val endAtElapsed: Long) : TimerStatus      // SystemClock.elapsedRealtime() ms
    data class Paused(val remainingMs: Long) : TimerStatus
    data object Finished : TimerStatus
}

data class TimerState(
    val id: String,                 // "pomodoro" or UUID for countdown timers
    val label: String,
    val phase: Phase?,              // null for plain countdowns
    val durationMs: Long,
    val status: TimerStatus,
    val round: Int = 1,
    val taskId: Long? = null,
)

@Entity data class SessionEntity(
    @PrimaryKey(autoGenerate = true) val id: Long = 0,
    val phase: Phase,
    val startedAtEpochMs: Long,     // wall clock, for stats only
    val plannedMs: Long,
    val actualMs: Long,
    val completed: Boolean,         // false = abandoned (plant wilts)
    val taskId: Long?,
    val tag: String?,
)

Timer engine rules (the most important part of the app)

  1. Never count ticks. Remaining time = endAtElapsed - SystemClock.elapsedRealtime(). A per-second coroutine only refreshes the UI. It never decrements a counter.
  2. Use the monotonic clock (elapsedRealtime) for timing and wall-clock time only for stats. Changing the device time or time zone must not affect a running timer.
  3. Persist on every state change. Write TimerState to DataStore or Room on start, pause, resume, skip and finish, so a killed process can be rebuilt exactly.
  4. Schedule the OS alarm on start and resume, and cancel it on pause and reset. Use setExactAndAllowWhileIdle with the ELAPSED_REALTIME_WAKEUP type. Use one PendingIntent per timer id (FLAG_IMMUTABLE) and a unique request code per timer.
  5. After a reboot, elapsedRealtime resets to zero. Before shutdown you cannot rely on anything, so also store endAtWallClock. In BOOT_COMPLETED, recompute the remaining time. If it is ≤ 0, post a "Timer finished while your phone was off" notification. Otherwise, reschedule.
  6. Put all timing logic behind a Clock interface, so tests can advance virtual time.

Background strategy

Situation Mechanism
App visible Compose collects StateFlow. A ~100 ms frame clock drives the smooth ring animation, and the text updates once a second.
App in background, timer running Ongoing notification with setUsesChronometer(true) + setChronometerCountDown(true) and setWhen(endAtWallClock). The OS draws the countdown, so there is no per-second update. On API 36+, use Notification.ProgressStyle with focus and break segments as a Live Update.
Timer ends (any state, including Doze or a killed app) Exact alarm → AlarmReceiver → TimerEngine.onFinished() → high-priority "alarm" channel notification with sound, vibration and a full-screen intent → auto-start the next phase if enabled.
Foreground service Run TimerService only while a timer is running or ringing, so the notification is not dismissible and the process stays warm. Declare foregroundServiceType="specialUse" with a clear subtype description. If ambient sound is playing, use mediaPlayback. Never use shortService, which times out after about 3 minutes.
Reboot BootReceiver (RECEIVE_BOOT_COMPLETED) rebuilds state and reschedules alarms. Do not start a mediaPlayback foreground service from BOOT_COMPLETED on Android 15+.

6. Instructions, best practices and advice for the coding agent

Build the timer engine and its tests first, and prove reliability on a real device before writing any polish. Most timer apps lose their rating on one complaint: "the alarm didn't ring."

Step-by-step build plan (each milestone ends with a green build + tests)

  1. M0: Scaffold. Set up the multi-module project, Hilt, Compose theme, version catalog, ktlint/detekt, a GitHub Actions CI job (./gradlew lint test assembleDebug) and an empty NavHost with 4 tabs.
  2. M1: Timer engine (pure Kotlin). Build TimerEngine, Clock, the Pomodoro cycle logic and state persistence. Unit tests must cover: start/pause/resume/skip/reset, the auto-cycle to a long break after N rounds, process death and restore, time-zone or clock change, and reboot recovery. Aim for 90%+ line coverage of :core:domain.
  3. M2: Platform layer. Add AlarmScheduler, AlarmReceiver, TimerService, NotificationController (chronometer countdown + ProgressStyle on API 36), BootReceiver, the permission primers and the full-screen alarm activity. Then run the manual test matrix below.
  4. M3: Focus screen. Build the progress ring (Canvas), the phase colour transition, controls, the task chip and the session-complete sheet.
  5. M4: Timers + stopwatch. Support multiple concurrent countdowns, presets, +1/+5 min and laps.
  6. M5: Stats, goals, streaks and garden. Add Room queries, charts and the reward visual.
  7. M6: Settings, onboarding, widget (Glance) and DND toggle.
  8. M7: Monetization. Add Play Billing (one-time + subscription, acknowledge purchases, restore, a server-less entitlement cache), the paywall, AdMob banner + UMP consent on the free tier only, and a "Pro" feature-flag wrapper.
  9. M8: Release hardening. Add Baseline Profiles, R8 full mode, Crashlytics, Play listing assets, the Data safety form, the exact-alarm and FGS declarations, and an internal testing track.

Do

  • Store endAt, not "seconds left". Derive everything from the clock.
  • Keep one source of truth (TimerEngine StateFlow). The UI, widget and notification only read from it.
  • Use collectAsStateWithLifecycle and stateIn(WhileSubscribed(5_000)) in ViewModels.
  • Put every action (start, pause and so on) through one entry point. The notification and widget buttons should call a BroadcastReceiver or the service, which calls the engine.
  • Ask for POST_NOTIFICATIONS at the moment the user starts the first timer, with a one-line rationale. Do not ask at app launch.
  • Check canUseFullScreenIntent() (Android 14+) and the exact-alarm permission at runtime. Show an in-app banner with a fix button if either is missing.
  • Handle OEM battery killers (Xiaomi, Samsung, Oppo, Huawei). Show a "keep timers reliable" help screen linking to battery-optimization settings, and check isIgnoringBatteryOptimizations. Never force the user to grant it.
  • Make every user-visible string a resource from day one, ready for localization (start with EN, ES, PT-BR, DE, JA, KO and ZH; Pomodoro apps are strong in Asia).
  • Write Compose previews for every screen in light, dark and font scale 2.0.

Don't

  • Don't use CountDownTimer, Handler loops or delay(1000) counting as the source of truth. They drift and die with the process.
  • Don't update the notification every second. Use the chronometer, or update at most once a minute.
  • Don't use WorkManager for the alarm itself. Its minimum interval and deferrable nature make it miss deadlines.
  • Don't hold a wake lock for the whole session or keep the CPU awake. The exact alarm wakes the device.
  • Don't show interstitial ads, rating prompts or the paywall during a running focus session.
  • Don't request Accessibility, UsageStats or overlay permissions in v1. They trigger extra Play review.
  • Don't put timer logic in Composables or Activities.

Manual test matrix (run on a physical device + API 26, 30, 34 and 36 emulators)

  • Start a 25-minute timer, lock the screen, wait. The alarm rings within ±1 s.
  • Start a timer, swipe the app away from Recents. The alarm still rings, and the notification is restored.
  • Force Doze (adb shell dumpsys deviceidle force-idle). The alarm still rings on time.
  • Start a timer, reboot the device mid-session. The timer is restored with the correct remaining time, or a "finished while off" notice appears.
  • Change the system time and time zone mid-session. The remaining time is unchanged.
  • Revoke the notification and exact-alarm permissions. The app explains the problem and still works in degraded mode.
  • Run 3 countdowns + 1 Pomodoro at the same time. Each rings once, with the correct label.
  • Pause and resume from the notification, widget and lock screen. All surfaces stay in sync within 1 s.
  • TalkBack navigation of every screen. Font scale 200% shows no clipped text.
  • Battery: a 60-minute background session uses < 1% battery on a mid-range device.

Play Store and policy checklist

  • Complete the Restricted permissions declaration for USE_EXACT_ALARM, the Foreground service declaration (with a short video of the timer notification), and the Full-screen intent declaration.
  • The Data safety form must match the SDKs used (AdMob, Crashlytics, Billing). Link the privacy policy in the app and the listing.
  • Listing: 8 screenshots (Focus, Timers, Stats, Garden, notification, widget, dark mode, Pro), a 30-second promo video and a feature graphic. Use keywords from competitor titles naturally: "Pomodoro timer", "focus timer", "study timer", "ADHD".
  • Ask for an in-app review after the 5th completed session, never after an abandoned one.

Definition of done for v1.0

All P0 features meet their acceptance criteria in Section 3, the manual test matrix passes on all four API levels, :core:domain coverage is ≥ 90%, there are no lint errors, Baseline Profiles are generated, and the release build is ≤ 15 MB.
