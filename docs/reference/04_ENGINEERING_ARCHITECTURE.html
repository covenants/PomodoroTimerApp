Architectural invariants

  1. One active session at a time on device. Enforce in a DB transaction or uniqueness logic.
  2. A pure domain reducer validates transitions. UI, notification and AlarmReceiver all dispatch identical commands through a single app use case.
  3. Persist state first, then schedule or cancel platform side effects; on restart reconcile DB with OS alarms.
  4. Every command has a deterministic eventId; stage-completion writes are idempotent to avoid duplicate rewards and history records.
  5. UI renders from StateFlow<TimerUiState>. Do not have several independent booleans for paused/completed/running.
  6. No Activity reference in timer repository; no unnecessary foreground service.

3 · Timer clock model: the most important engineering section

Principle: a countdown is the difference between an authoritative deadline and the current monotonic clock. A loop that decrements “secondsLeft” once per second will drift, freeze in Doze, and reset after process death. Treat per-second UI ticks as display refreshes only.

Clock & restore strategy

  1. Inject Clock with elapsedRealtimeMillis(), wallClockMillis(), zoneId() and optionally boot identity.
  2. On Start/Resume, persist deadlineElapsedMs = nowElapsed + remainingMs, expectedWallDeadlineMs = nowWall + remainingMs, bootMarker, stageVersion and state, in one transaction.
  3. While on the same boot, remaining is max(0, deadlineElapsedMs - nowElapsed); robust to system clock/time-zone changes and sleep.
  4. On reboot, monotonic time resets. If a boot identity is reliably available, detect boot change. Otherwise compare persisted anchors and elapsed behavior, and conservatively reconstruct from expected wall deadline. Mark a recovered deadline as approximate if manual clock changes make it ambiguous.
  5. On Pause, compute remaining from monotonic, persist PAUSED with saved remaining, clear deadline and cancel scheduled alarm. On Resume compute a new deadline.
  6. On app restore or alarm callback, call reconcileDue(). Mark stage COMPLETE only once, using sessionId + stageIndex + version uniqueness.
  7. For Focus stage completion: record actual focus time based on active time, not elapsed time spent paused. Do not count Quick Timer as focused minutes unless the user explicitly opted in.

Kotlin reference API (architecture sketch, not a full APK)

interface TimeSource {
    fun elapsedRealtimeMs(): Long
    fun wallClockMs(): Long
    fun bootMarker(): String? // best effort, platform adapter
}

enum class TimerMode { FOCUS, COUNTDOWN, STOPWATCH }
enum class TimerStatus { IDLE, RUNNING, PAUSED, COMPLETED, CANCELED }
enum class FocusStage { WORK, SHORT_BREAK, LONG_BREAK }

data class TimerSnapshot(
    val id: String,
    val mode: TimerMode,
    val status: TimerStatus,
    val stage: FocusStage?,
    val stageIndex: Int,
    val totalDurationMs: Long,
    val remainingWhenPausedMs: Long,
    val endElapsedRealtimeMs: Long?,
    val expectedWallEndMs: Long?,
    val bootMarker: String?,
    val version: Long
)

fun remainingMs(snapshot: TimerSnapshot, clock: TimeSource): Long = when (snapshot.status) {
    TimerStatus.RUNNING -> {
        val deadline = snapshot.endElapsedRealtimeMs
        if (deadline != null && snapshot.bootMarker == clock.bootMarker()) {
            (deadline - clock.elapsedRealtimeMs()).coerceAtLeast(0)
        } else {
            // Explicitly approximate after reboot / unknown boot identity.
            ((snapshot.expectedWallEndMs ?: clock.wallClockMs()) -
                clock.wallClockMs()).coerceAtLeast(0)
        }
    }
    TimerStatus.PAUSED -> snapshot.remainingWhenPausedMs
    TimerStatus.IDLE -> snapshot.totalDurationMs
    else -> 0L
}

// The repository must enforce command/version/idempotency semantics in a transaction.
// Never run a foreground one-second loop just to make time elapse.

Stopwatch-specific rule: use an accumulated active-duration counter plus a current monotonic start anchor, rather than an end deadline; pause must exclude idle intervals and reboot reconstruction must disclose its approximation.

For production, represent domain enums using stable string serializers; maintain migration tests. Keep user-facing routine definitions in DataStore or dedicated Room routine table if complex. Avoid embedding collected task text in diagnostic events. Store timestamps in UTC epoch milliseconds; calculate daily buckets with the user’s selected timezone rather than storing local date-only as authoritative truth.

Important reporting rules

  • Store work, short-break, and long-break durations separately. Only completed work counts toward completed Pomodoros; optionally show partially focused time as its own metric.
  • Every session has mode, stageIndex, status, and optional taskId. A stage event is immutable.
  • Do not silently merge duplicates when importing data. Define stable UUID and conflict behavior.
  • Export a versioned CSV with clear columns, UTC times and local display timezone. Support delete and undo confirmation.

5 · Android scheduling, notification and policy guidance

AlarmManager

Schedule only the upcoming stage-end event. Use a stable PendingIntent identity and immutable flags. Exact alarms on Android 12+ have a special access gate. Evaluate eligibility and user expectations carefully; use canScheduleExactAlarms() before invoking APIs requiring it. If inaccessible, preserve correct elapsed time and show honest alert limitations; consider permitted inexact alarm behavior for best-effort notifications.

Official alarm guidance

Foreground Service

Do not assume a persistent foreground service is a solution to all lifecycle problems. Android 14+ requires service type and declaration; a timer-only FGS must be justified against platform-supported alternatives and Play policy. Prefer finite stage-end alarms + persistent state. Add a compliant user-visible FGS only after a documented need and policy assessment.

Official foreground service types

Notifications / DND

Android 13+ requests POST_NOTIFICATIONS. Use channels for completion / active-status alerts. Let users mute alerts independently; never bypass DND. Notification action broadcasts must send validated session/version and dispatch through repository, not mutate a ViewModel directly.

Notification design

App-blocking scope

Not part of MVP. AccessibilityService use is sensitive, requires Play listing disclosures and may need prominent consent. Do not market as a disability access app unless truly qualified. Prefer no usage/accessibility permission. Do not attempt to restrict system safety functions.

Google Play policy

Suggested manifest policy

Declare only the permissions implemented and approved by policy. For the first prototype use POST_NOTIFICATIONS where relevant and optionally RECEIVE_BOOT_COMPLETED for recovery. SCHEDULE_EXACT_ALARM requires a concrete user-facing precise timer justification plus feature/grant check; not an unconditional copy-paste permission. USE_EXACT_ALARM has a narrower policy eligibility scope—do not substitute it casually. Never ship QUERY_ALL_PACKAGES or AccessibilityService for MVP. Keep services exported=false unless a supported explicit externally initiated action demands otherwise.

7 · Privacy, billing, distribution and risk controls

  • Offline-first: no backend or account required; task names and focus history stay local. Avoid indiscriminate SDK ingestion.
  • Store integrity: Play Integrity only if a later backend requires it; never block offline timing due to network failures.
  • Entitlements: Google Play Billing when paywall launches; verify on secure backend if offering shared cloud entitlements. Define offline entitlement grace behavior; support restoring purchases.
  • Export: Android SAF share/save flow with explicit user action and appropriate file provider or document creation; avoid broad storage permission.
  • Security: exported receivers and PendingIntents audited; immutable flags, unique request codes, minimal permissions, dependency updates, CI static analysis.
  • Observability: sanitized crash traces, no task text in logs, optional anonymous telemetry, retention policy, visible delete-data option.
  • Play requirements: account data deletion requirements if accounts added, Data Safety accuracy, subscriptions disclosed and canceled via standard Google Play UI, screenshots consistent with reality, content-rating questionnaire and relevant target API updates.
