A · Copy-ready master coding-agent prompt

You are the Principal Android Engineer, mobile product designer and release QA owner for Orbit — Focus & Timer. Implement a production-quality, Android-native, offline-first Android application using Kotlin, Jetpack Compose, Material 3, Room, DataStore, Hilt, Coroutines/StateFlow and appropriately justified Android timer scheduling APIs. “Orbit” is a working title and must not be treated as brand cleared. Work directly in the repository; do not produce only mock code.

Read the specifications first: 00_START_HERE.html, 01_COMPETITOR_RESEARCH.html, 02_ANDROID_PRODUCT_PRD.html, 03_UI_DESIGN_GALLERY.html, 04_ENGINEERING_ARCHITECTURE.html. Parse or open HTML as needed. The original phone UI references and PNG exports are visual targets, but Compose must render native controls and state. Never copy competitors’ proprietary illustrations or exact app trade dress.

Goals

  1. Create an elegant, stable, offline, no-login dual-mode Android app: Focus/Pomodoro and Countdown/Stopwatch. User starts a 25-minute timer with a single action. Both modes are first-class.
  2. Implement accurate timer behavior across app backgrounding, screen off, Activity recreation, process death, timezone change, device reboot and special-alarm-permission denial. Never implement countdown correctness by decrementing a 1-second mutable counter.
  3. Ship the original Midnight Orbit theme, responsive small/large screen layouts, light/aurora theme support, TalkBack, reduced motion, haptics settings and high contrast, plus the nine screen layouts from the visual gallery.
  4. Track focus sessions locally, support simple tasks and tags, offer today/week insights and heatmap, allow all data to be deleted and exportable in a later step. Do not require user contact data.
  5. Keep core timing free, with no launch paywall and no background permissions unrelated to timing. Premium code may be feature-gated behind an interface, but do not ship fake billing endpoints or claim subscriptions work without Play integration.

Constraints

  • Native Kotlin + Compose (not React Native, not Flutter); minimum API 26 proposed; target the latest stable Google Play-compliant SDK.
  • No required backend, Firebase account, cloud API or internet for core flow; offline is mandatory.
  • Use Room for authoritative sessions/tasks/event history and DataStore for preferences. Timer commands are serialized through repository transitions; completion idempotent via unique event ID.
  • Timer uses Android elapsedRealtime on same boot and a carefully marked wall-clock fallback after restart/reboot; schedulers are for side effects, never truth.
  • No indefinite foreground service by default; exact-alarm request and permissions must satisfy official Android and Play policies. Handle denied special access safely.
  • Do not ask for AccessibilityService / QUERY_ALL_PACKAGES / UsageStats in MVP. App blocking is out of scope.
  • Never ask for broad storage permissions. Export via Android SAF. No hardcoded API keys.
  • Use pinned versions in Gradle version catalog, Kotlin K2 where stable for chosen tools, format/lint/test CI and real-device manual test plan.
  • Implement safe retry, cancellation, lifecycle and DB migration logic. No unstructured global coroutine scopes or view-owned timing services.
  • Persist stage and alarm identity. Notification actions and Activity actions must dispatch through the same command processor.

Scope progression: build in independently testable phases

Phase 0: Inspect repo and environment, create or evolve Gradle project, list risks, document package name and source-of-truth model. Write ADRs for timebase and alarm policy.

Phase 1: Create domain models, pure reducer, injected clock, Room tables + migrations, DataStore config, repository, comprehensive clock/state tests. Run tests; no visual code until this is green.

Phase 2: Implement Pomodoro sequence, countdown, stopwatch, start/pause/resume/skip/stop/extend, one active timer, stage end scheduling, notification channels and actions, process restore and receiver; run integration tests. Build a manual matrix for battery saver, API 26/33/34/35+ and OEM devices.

Phase 3: Implement responsive Compose screens from reference UI. Use Material 3, Canvas orbit, semantic timer labels, theme tokens, explicit action states, animations with reduced-motion option, voice/touch accessibility and notifications.

Phase 4: Tasks, tags, local metrics, heatmap, home widget, profiles, silent mode/audio and settings. Include localization-ready string resources and modern Android back navigation.

Phase 5: Finish quality, privacy and release: test against requirements; lint, instrumented tests, release bundle, signing instructions, Store listing asset checklist, permissions declaration and Data Safety answers. Do not invent test results—report executed commands and real outputs.

Acceptance gates

G1: JVM reducer tests pass; time changes and pause handled. G2: no duplicate completion after replayed alarms/rapid tapping; process death restoration passes. G3: critical screens render on 360dp and tablet; TalkBack and reduced-motion checks. G4: core app works with notification and exact-alarm permissions denied. G5: assembleDebug, unit tests and lint pass. G6: README, architecture decisions, test matrix, screenshots and release/policy checklist exist.

Required deliverables in repo

Complete source, Gradle wrapper, version catalog, run instructions, APK/debug build artifact if environment permits, representative UI captures, test evidence, architecture decision records, privacy policy draft and Store listing copy. Report outstanding risks and missing device tests; never say “production ready” without passing release gates.

Execution rule: Do not stop after architecture or scaffolding. Implement an end-to-end working vertical slice first (Focus start → background → completion → history) and then iterate. Whenever the environment blocks a device-level test, log the blocker and still complete all runnable unit/integration tests. Use sound production engineering judgment rather than asking cosmetic clarification questions.

B · Detailed task backlog by sequence

Epic 0 · Repository setup

0.1–0.6: Bootstrapping

  • Create Gradle Kotlin DSL project and module dependency graph, clean assembleDebug.
  • Configure Hilt, Compose, Room, DataStore, Kotlin tests and consistent lint.
  • Create TimeSource, fake clock, DTO invariants and ADR-001/002.
  • Choose package name and application ID as config values; do not publish under placeholder name without clearance.
Epic 1 · Clock core

1.1–1.9: Timer state and persistence

  • Implement reducer/state events, explicit invalid-transition errors, reducer invariants and atomic command dispatch.
  • Define session transaction, uniqueness constraints, stage version, event deduplication.
  • Implement monotonic deadlines, pause duration, active elapsed time and reboot fallback.
  • Implement sequence engine for short/long breaks and auto-start preferences.
  • Unit tests for time jump, duplicate alarm, pause, skip, reboot and day rollover.
Epic 2 · Android platform integration

2.1–2.8: Scheduling & notification

  • AlarmReceiver reads persisted state and validates session/version before completing.
  • Schedule at due timestamp with policy-safe exact/inexact fallback and permission checks.
  • POST_NOTIFICATIONS request context; completion channel; Pause/Resume/Stop actions.
  • Boot and app restore reconciliation, stable PendingIntent identity and no double schedule.
  • No unconditional FGS. If proposing one, write a policy analysis and test alternative first.
Epic 3 · Compose visual implementation

3.1–3.9: Build all nine screen references

  • Implement design system typography/tokens/spacing; native responsive layout.
  • Timer/Focusing/Countdown/Stopwatch screens with single CTA and safe actions.
  • Tasks, insights, original constellation, routine editor, settings, optional commerce placeholder.
  • Navigation with stable route types; state restoration, immersive keyboard and accessible input.
  • Material 3 semantics, dark/light/aurora, large fonts, tablets, reduce-motion.
Epic 4 · Growth without privacy tradeoffs

4.1–4.6: Delight and useful history

  • Session history, date-grouped focus minutes and chart queries.
  • Simple task linking, completion, lightweight quick-add.
  • Optional theme, ambient audio and haptics (no default background audio).
  • Optional Glance home widget and review prompt only after satisfying user value.
  • Data export and delete with confirmation and graceful handling of failure.
Epic 5 · QA and Play Store

5.1–5.9: Release gates

  • Unit and integration test suite; run through all documented T-001–T-016 cases feasible in environment.
  • Test Android notifications denial, exact alarm denial, device idle, background, recovery and OEM limitations.
  • Configure app icon, adaptive icon, splash, Play listing text and truthful screenshots.
  • Document privacy, data safety, permissions, legal terms if billing, and app attribution.
  • Produce versioned release .aab and explicit Google Play Console handoff guide.

D · Known risks and decision policies

Biggest risk: clock correctness

Prioritize invariants and deterministic tests over animation polish. Require rollback/reconcile on DB side-effect errors. Test long durations, rapid taps, alarm duplicate delivery and reboot. A platform alarm is an alert, never source of truth.

Policy risk: alarms / FGS

No guarantee notification every exact second on every device. Follow Android docs and Play special permission policy. Record which feature was actually tested on which API level and which user grants.

Business risk: insufficient differentiation

Do not clone Forest gamification. Lead with polished, low-friction dual timer, exceptional reliability, delight and pricing trust. Validate feature requests through reviews and beta.

Scope risk: building a superapp

Do not add habits calendar, team chat, cloud, AI coaching or app blocking to MVP. Land a complete vertical slice before expanding the backlog.
